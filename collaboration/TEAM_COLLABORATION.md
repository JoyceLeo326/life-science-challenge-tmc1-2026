# 今日三人协作

## 分工与目录

| 角色 | 负责内容 | 主要写入目录 | 审阅安排 |
|---|---|---|---|
| A：总控与发布 | 建立任务、维护状态、核对清单、决定发布范围 | `collaboration/`；发布清单由 A 维护 | A 的 PR 由 B 或 C 审阅 |
| B：科学材料 | 摘要、评审文字、演示稿与图注，逐项标注来源和限制 | `science/` | C 核对数字与图件来源，A 验收交付 |
| C：计算复现 | 公开代码、依赖、输入版本、参数、输出和运行记录 | `code/` | B 核对科学解释，A 验收交付 |

各人负责本目录的实际改动。跨目录修改先在 Issue 或 PR 说明，由该目录负责人落实。每个 Issue 只有一位负责人；用户名确认后再指派。

## 今天的发布序列

1. A 核对公开仓库的 `main` 提交、目录与写入权限，创建三个 Issue；A/B/C 分别认领。
2. 各人从最新 `main` 建独立分支，先提交可审阅的真实工作成果。**每批成果完成后 5 分钟内提交并 push**，在 Issue 留下提交链接和剩余缺口。
3. B、C 先提交各自 PR，写清输入、来源、方法、输出、限制和证据。非作者审阅、修正后合并。A 再基于已合并内容更新状态与发布清单，提交 A 的 PR，交 B 或 C 审阅。
4. A 以合并后的 `main` 为准核对文件与 SHA256，再决定是否建立 tag/Release。范围不足时记录缺口和阻塞原因；只发布已核查内容。
5. 赛事官网提交由实际提交人办理，并在取得真实回执后更新状态。公开仓库的发布与赛事官网提交分别记录。

## 审阅与纠错

每个 PR 至少有一名非作者审阅者。发现错误时，在 PR 中指出文件、影响和依据；负责人修正后重新请求审阅。涉及敏感信息的内容先停止合并与发布，由 A 协调移除并处理已公开版本。不得在 Issue 或 PR 中粘贴凭据或个人资料。

计算筛选分数、候选排序与机制推断均按计算研究描述。结合、激活、抑制、疗效等实验结论须有相应证据；未完成的湿实验写为待办。R1、R2、R3 的数据和结论要标清版本，不能混用。
